# 무엇을 어떻게 판정할까

검사 설계자가 실행 전에 읽고, 통합 검토자가 판정 근거를 다시 찾을 때 쓰는 문서다. 아래 예시는 로컬 영수증 내보내기 기능에 대한 **설계 예시**다. 패키지 데모에서 실제 관찰한 내용은 각 시도의 정규 실행 기록에 있다.

## 기준부터 고정한다

1. 대상 리비전, 제품 목표, 선택한 스킬 규칙, 프로젝트 요구사항을 각각 식별자·버전·원문 스냅샷으로 고정한다. “빠르게 내보내기”처럼 결과를 가를 수 없는 문장은 기준 소유자와 관찰 가능한 조건으로 구체화한다. 승인되지 않은 수치나 요구는 가설로 남긴다.
2. 검사마다 해당 기준 ID, 통과 조건, 필요한 환경 능력, 입력 자료, 기대값의 근거를 적는다. 좋은 통과 조건은 같은 증거를 받은 다른 검토자도 참·거짓을 가릴 수 있다. 사용할 기준이 모든 검사와 연결되는지 역방향으로도 확인한다.
3. 예를 들어 `G-02@1`이 “오프라인에서 최종 영수증을 얻는다”, `R-07@3`이 “중복 요청은 파일 한 개로 끝난다”이면, 시스템 검사에 네트워크 없는 로컬 프로필과 같은 요청 두 건을 배정한다. 산출 파일 수 1개, 예상 합계와 일치하는 내용을 통과 조건으로 고정한다. 실제 파일 목록과 내용 대조 로그를 증거로 남긴다. 파일 수 2개이면 한 합계가 정확해도 이 검사는 실패다.
4. 기준 또는 검사 범위를 바꾸면 바뀐 이유와 직전 기록을 연결한 새 시도를 만든다. 지난 통과는 비교 자료로만 쓴다. 이번 시도에 대응하는 관찰이 있어야 이번 통과를 부여한다.

계획에는 표준별 판본과 **이 시도에서 적용한 이유 또는 비적용 사유**를 남긴다. 예를 들어 모바일 사용 과업이 계약 밖이면 그 맥락을 제외한 이유를 쓴다. 계약에 모바일 지원이 있고 단말을 확보하지 못했다면 모바일 검사를 남기고 차단 처리한다. 비적용 사유는 통과 증거가 될 수 없다.

검사별 대응은 [표준 목록](../schemas/standards.json)과 계획 1.1의 `standards`로 기록한다. 검사 목적별로 붙일 표준은 [에이전트 지침](../SKILL.md)의 용도별 표준 선택을 따른다.

## 첫 판정을 나누는 여섯 역할

블랙박스 역할에는 버전 고정된 요구와 공개 인터페이스, 허용된 환경, 테스트 입력과 관찰 결과를 제공한다. 화이트박스 역할에는 필요한 소스·설계·설정의 고정 스냅샷도 제공한다. 어느 쪽도 첫 판정 전 다른 역할의 해석이나 현재 시도의 예상 판정을 받지 않는다. 아래 여섯 역할은 ITR에서 제안하는 분업이다.

| 역할 ID | 담당 질문 | 첫 판정에 남길 예 |
| --- | --- | --- |
| `bb_goal` 목표 | 공표한 동작이 목표를 달성하는가? | 영수증 출력의 합계와 독립적으로 계산한 기대 합계 |
| `bb_context` 사용 맥락 | 지정된 사용자가 주어진 환경에서 과업을 마칠 수 있는가? | 로컬 오프라인 프로필, 수행한 과업 순서와 최종 파일 |
| `bb_boundary` 경계 | 입력의 경계와 반복 요청에서 공개 계약을 지키는가? | 0·1·최대 허용 수량과 최대값 바로 바깥의 기대·실제 결과 |
| `wb_logic` 내부 로직 | 분기와 상태 전이가 요구사항을 보존하는가? | 고정 리비전의 계산 경로, 소수점 처리, 확인한 분기 |
| `wb_contract` 구성요소 계약 | 호출자와 제공자가 값·오류·재시도 의미를 공유하는가? | 내보내기 함수와 저장소 인터페이스가 중복 요청을 다루는 위치 |
| `wb_config` 설정·방어 검토 | 설정 기본값과 오류 처리, 로그에 대한 프로젝트 규칙이 구현됐는가? | 예시 설정과 소스에서 확인한 허용 경로·로그 필드, 파일 위치 |

보안 품질은 로컬 코드·설정의 방어적 인스펙션으로 제한한다. 소스의 로그 필드 허용 목록이나 예시 설정을 검토할 때는 합성 자료를 사용한다. 공격, 익스플로잇, 침투, 실서비스 자동화는 범위 밖이다.

### 첫 판정의 격리와 통합

1. 조정자가 입력 묶음과 역할별 검사 ID를 고정한다. 역할별 별도 컨텍스트·작업공간을 제공하고, 공유 폴더에 다른 역할의 판정이나 아직 확정되지 않은 통합본을 노출하지 않는다. 같은 모델을 사용해도 역할별 입력·도구 접근을 분리한다. 격리할 수 없는 환경에서는 독립 검토가 충족되지 않았음을 기록한다.
2. 각 역할은 자기 관찰, 적용 기준, 기대·실제 차이, 증거 ID, 판정, 완료 시각을 독립적으로 봉인한다. 선행 조건 누락이나 수행 생략도 그 역할의 슬롯에 이유와 함께 남긴다. 직전 시도의 재현 입력을 사용할 때에도 조정자가 다른 역할의 현재 판정·해석을 제거한다.
3. 조정자는 모든 배정 슬롯이 닫힌 뒤에만 첫 판정을 같이 읽는다. 동일한 산출물·조건에 대한 의견인지 확인하고, 증거 경로와 해시를 대조한다. 관찰이 충돌하면 재현 조건을 쪼개고 두 원본을 보존한다. 이미 입증된 기준 위반은 실패로 유지한다. 근거가 모자란 판정은 차단 사유와 추가 관찰 계획을 남긴다. 다수결로 통과시키지 않는다.
4. 같은 결함으로 합칠 때는 위반한 기준, 영향 받는 동작, 입력이나 관찰 결과를 비교하고 공통 지문과 원 관찰들을 잇는다. 한 원인 가설만으로 별개 증상을 합치지 않는다. 원인 확정에는 확인 가능한 별도 증거가 필요하다. 가설은 미확정으로 유지하고 다음 회귀 검사로 해소한다.
5. 통합 판정은 기술적 검사 결과다. 발주자/사용자 승인에는 **해당 권한자의 명시적 의사표시**, 누구의 승인인지, 대상 리비전과 시각이 필요하다. 인수 시나리오가 모두 통과해도 그 사실만으로 승인 상태를 갱신하지 않는다. 나중에 도착한 승인 또는 정정은 기존 시도를 보존한 새 기록으로 연결한다.

다른 AI 연결과 독립 리뷰 인프라는 어댑터 구현에서 제공할 수 있는 능력이다. 한 프로세스의 합성 예제에서 얻은 결과는 그 예제의 관찰 범위로 해석한다.

## 산출물 인스펙션과 실행 테스트

인스펙션은 지정 리비전의 문서·코드·설정을 읽어 기준 위반을 찾는다. 증거에는 위치, 검토한 조건, 직접 관찰을 묶는다. 실행 테스트는 지정한 입력으로 실제 대상이나 명시한 대역을 실행한다. 실행기·환경·입력·예상·실제 출력을 연결한다. 같은 목표에 두 방법을 쓰면 검사 ID와 증거를 따로 준다. 설계에 재시도가 적혀 있어도 실행 중 중복 저장을 막았다는 증거는 따로 얻는다.

| 실행 수준 | 영수증 내보내기 설계 예시 | 통과를 판단하는 증거 |
| --- | --- | --- |
| 단위 | 고정된 반올림 규칙으로 합계 계산 함수의 경계값 확인 | 입력·기대·실제 값, 함수 결과 |
| 통합 | 내보내기 로직과 임시 파일 저장소를 연결하고 같은 요청을 두 번 호출 | 호출 순서, 파일 수와 내용, 사용한 대역의 범위 |
| 시스템 | 로컬 설치본의 공개 CLI나 브라우저 화면에서 주문부터 내보내기까지 수행 | 실제 진입점, 실행 환경, 종료 상태와 파일 내용 |
| 시스템 간 통합 · 선택 | 독립된 로컬 주문 시스템과 회계 소비자가 합성 영수증을 교환 | 생산자·소비자 버전, 상관 ID, 수신·처리 결과. 스텁만 썼다면 실제 상대 시스템 상호 운용성은 미확인 |
| 인수 시나리오 | 합의된 사용자 역할·맥락에서 오프라인 주문 증빙을 발급하고 다시 연다 | 과업 완료 조건과 출력, 불완전한 단계. 실제 인수 의사표시는 별도 승인 기록 |

단위 → 통합 → 시스템 → 인수 시나리오의 의존성을 계획에 적고 필요할 때 시스템 간 통합을 끼운다. 실패가 다른 검사의 전제까지 깨면 해당 검사를 차단한다. 독립적으로 관찰할 수 있는 경로는 계속 진행해 증거를 남긴다. 특정 브라우저·OS·시뮬레이터·실기기 능력이 필수면 일치하는 실행기를 선택한다. 대체 환경에서 얻은 성공에는 원래 환경의 통과 지위를 부여하지 않는다.

## 정밀 모드와 일상 변경분 모드

| 결정 | 정밀 모드 | 일상 변경분 모드 |
| --- | --- | --- |
| 시작점 | 후보 리비전의 전체 기준과 지원 환경 | 직전 불변 기록, 기준 리비전과 현재 리비전, 파일·계약·환경 변화 |
| 검사 선택 | 필수 기준과 지원 조건별로 인스펙션·실행 검사와 여섯 역할을 배정 | 변경 기준에서 호출자·사용 흐름·과거 결함의 회귀 검사까지 영향선을 추적하고 직접 영향과 공통 핵심 흐름을 선정 |
| 미확인 범위 | 필요한 능력 부재는 차단으로, 실행 생략은 미실행으로 기록 | 선택하지 않은 기존 검사는 범위와 이유를 남겨 전제품 통과로 읽히지 않게 한다 |
| 범위 확대 | 새 기준·모순은 새 시도에서 계획을 보완 | 비교 기준이 없거나 공통 계약·저장 형식 변경 등으로 영향을 한정할 수 없으면 정밀 모드로 새 계획을 만든다 |
| 인계 | 기준별 증거, 실패와 차단, 미해결 승인 | 비교한 시도·리비전, 미검사 범위, 회귀 상태와 다음 정밀 확인 대상 |

예를 들어 금액 반올림 방식이 바뀌면 합계 단위 검사, 저장소로 보내는 금액의 통합 검사, 영수증 최종 합계와 기존 반올림 결함의 회귀 검사를 포함한다. 관련 없는 화면에 대한 이전 통과는 해당 시도의 기록에 남긴다. 영향이 불분명한 공통 내보내기 형식까지 바뀌면 계획 범위를 다시 잡는다.

## 판정 읽기

- **통과**는 해당 조건을 수행하고 관찰 결과가 기준을 만족하며 출처를 검증할 수 있을 때 부여한다. **실패**는 수행 중 확인한 기준 위반이다.
- **차단**은 필요한 환경·선행 조건·근거가 부족해 판정을 완료할 수 없는 경우다. **미실행**은 이번 시도에서 검사를 수행하지 않은 경우다. 둘 다 사유와 후속 조치를 남긴다.
- 단계별 수치는 고유 검사 ID별 최종 상태에서 계산한다. 중복 제거한 결함 수는 결함 지문에서 계산한다. 예를 들어 세 검사가 같은 저장 중복을 입증하면 실패 검사 3건, 확인된 중복 제거 결함 1건으로 표시할 수 있다.
- 실패 세부에는 목표 ID와 버전, 재현 입력, 로그나 캡처의 위치, 확인된 원인과 남은 가설, 최소 수정 방향, 다음 회귀 검사를 함께 둔다. 새 시도에서만 재실행 결과를 추가한다.
