# 검증과 릴리스 게이트

기록이 온전하면 실패한 제품도 정확하게 보고할 수 있다. ITR은 기록 유효성, 제품의 기술 판정, 사람이 하는 최종 승인을 따로 남긴다.

| 게이트 | 통과 조건 | 조건이 충족되지 않을 때 |
|---|---|---|
| 1. 기준 고정 | 목표·선택 규칙·프로젝트 요구사항의 버전과 제품 리비전이 있고, 선택 기준별로 실제 검사와 통과 조건이 있다. | 무근거한 기준 판정을 보류한다. 수정한 기준으로 새 회차를 연다. |
| 2. 실행 준비 | 검사별 방법·단계·역할·능력과 데이터가 주어진다. 환경 능력이 실제 대상의 관찰 조건을 충족한다. | 필수 능력 또는 권한 부재는 차단, 계획 밖 항목은 사유가 있는 미실행이다. |
| 3. 증거 | 수행한 검사에 기대·관찰 결과와 열 수 있는 증거가 있으며 바이트 해시가 일치한다. 격리된 최초 판정과 통합 근거를 구별할 수 있다. | 경로 누락, 해시 불일치, 서로 다른 기준 버전은 기록 오류로 보고한다. 기존 결과는 보존한다. |
| 4. 기술 판정 | 이번 범위에 선택한 모든 검사가 증거를 갖고 통과한다. 실패는 깨진 기준과 회귀 검사를 가리킨다. | 선택된 검사에 실패가 하나라도 있으면 실패, 실패 없이 차단이 있으면 차단이다. 남은 선택 검사 미실행은 통과를 막는다. |
| 5. 변경 회귀 | 닫으려는 결함마다 이전 fingerprint·원본을 확인하고 같은 조건으로 재검사한 근거가 있다. 기준 변경이 있으면 따로 설명한다. | 증상이 사라졌다는 추정만으로 결함을 닫을 수 없다. 관련 환경이 없으면 회귀 확인도 차단이다. |
| 6. 인수 및 릴리스 | 예정된 인수 시나리오를 수행했다. 발주자·사용자 승인이 필요한 납품이면 별도 승인의 범위·리비전·시각·증거도 확보한다. | 인수 시나리오가 통과해도 사람의 서명은 `not_requested` 또는 `pending` 상태로 남을 수 있다. |

계획에서 제외한 검사는 `selected: false`와 미실행 사유로 추적한다. 선택된 검사의 판정 집계와 전체 범위의 누락을 한 화면에서 확인한다. 좁은 변경분 게이트 통과를 전체 제품의 출시 승인으로 일반화할 수 없다. 필수 범위 변경은 고정 입력과 사유에서 확인할 수 있어야 한다.

## 충돌하는 근거를 만났을 때

실행 로그의 입력과 빌드가 같은지, 검토가 서로 다른 환경·조건을 가리키는지 확인한다. 직접 반례가 있으면 동등한 조건에서 재검사한다. 확인 전에는 원인을 가설로 남긴다. 인스펙션의 긍정 의견이 실패한 실행 증거를 상쇄하지 않는다. 관련 근거가 부족하거나 다른 조건에서 관찰했다면 두 관찰을 보존하고 새 검사로 분해한다.

## 스킬 패키지 출하 확인

1. README의 명령을 깨끗한 로컬 저장 위치에서 실행한다. 네트워크와 자격 증명 없이 정상·실패·차단·미실행이 기록되는지 본다.
2. 시도 충돌, 정정/재실행 및 새 회차의 이전 기록 바이트와 증거가 보존되는지 확인한다. 변조된 복사본, 잘못된 링크, 지원하지 않는 형식이 유효하다고 판정되지 않는지 확인한다.
3. 정규 기록과 화면, MD·인쇄본의 회차/시도·검사 결과·고유 결함·사람의 승인 상태를 대조한다. 화면에서는 증거 상세와 현재 작업 탐색을 확인한다.
4. 릴리스에 넣은 파일의 해시와 ZIP 무결성을 확인한다. 패키지에서 실제 수행한 시험·실행 환경·제약은 [검증 기록](../VERIFICATION.ko.md)에 남긴다.

이것은 ITR 초안의 운영 정책이다. 표준 활용 근거와 각 표준을 적용한 범위는 [평가 절차](assessment.ko.md)에 있다.
