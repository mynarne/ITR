# 실행 기록과 어댑터

ITR의 교환 단위는 **완결된 시도 하나와 그 증거 파일들**이다. 다른 에이전트는 같은 운영체제·모델·대화 이력 없이 이 묶음을 읽을 수 있다. 합성 실행기와 승인된 일반 프로젝트 실행기가 이 형식의 참조 구현이다. 다른 제품의 실행기를 붙일 때는 아래 계약을 사용한다.

## 기록을 따라 읽는 순서

| 질문 | 기록에서 찾을 곳 |
|---|---|
| 무엇을 약속했는가? | `input.product`, 제품의 `revision`, 버전 고정한 `baselines[]`. 유형은 제품 목표 `goal`, 선택된 스킬의 `rule`, 프로젝트 `requirement`다. |
| 무엇을 관찰하면 통과인가? | `input.checks[].criteria`가 기준 ID를 가리킨다. `pass_condition`에는 대상, 자극, 기대 관찰값과 비교법을 쓴다. 여러 기준의 조건이 다르면 검사를 나눈다. |
| 어느 환경에서 무엇을 했는가? | 계획의 능력 목록·단계·방법·역할과, 순번이 붙은 `events`를 읽는다. `seq`는 재생 순서다. 서로 다른 검사의 실행 구간은 겹칠 수 있다. |
| 관찰값을 다시 볼 수 있는가? | `results[].evidence_ids` → `evidence[].check_id/path/sha256` → 시도 폴더 내 실제 바이트. 각 결과의 `detail`과 증거를 통과 조건에 대조한다. |
| 누가 언제 처음 판단했는가? | `reviews`의 역할·검사·근거·봉인 시각. 실제 독립성이 필요한 프로젝트는 검토자 배정과 입력 격리 방식도 증거에 기록한다. |
| 무엇을 고치고 다시 검사하는가? | `defects`의 관찰·기준·검사·증거, 원인·가설, 최소 수정 방향과 다음 회귀 검사. 동일 결함은 검사가 여러 개여도 fingerprint 하나로 센다. |
| 기술 결과와 승인 상태는? | `decision`은 선택 범위의 기술 판정, `approval`은 별도 권한자의 의사 표시다. 승인/거부에는 당사자·범위 및 리비전·시각·증거 참조가 필요하다. |

정확한 필드·타입·상태 문자열은 [스키마](../schemas/record.schema.json)에 정의한다. 체크·증거·결함의 ID는 기록 내부에서 해석한다. 저장소를 넘겨 이전 기록을 찾을 때는 run ID, 회차, attempt, 경로와 해시를 함께 확인한다. 시각을 표시할 때는 KST(UTC+09:00)를 사용한다. 결과를 다시 취합할 때 버전을 먼저 확인한다. 지원하지 않는 버전은 그대로 보존하고 변환기를 선택한다. 필요한 제작자별 메타데이터는 최상위 `extensions`에 둔다.

## 어댑터 계약

| 경계 | 받아야 할 것 | 돌려줄 것 / 책임 |
|---|---|---|
| 기준 및 계획 | 제품 스냅샷, 의뢰 범위, 선택된 스킬과 규칙 버전, 프로젝트 요구사항 | 고정 입력, 기준별 검사와 관찰 조건. 대상 산출물의 digest 또는 리비전. 적용한 표준 관점과 제외 사유. |
| 환경 확인 | 검사별 필요 능력, 허용된 로컬 환경 | 실제 확인한 파일/프로세스/브라우저/운영체제/시뮬레이터/실기기 능력, 버전·제약·확인 근거. 능력을 선언한 것만으로 동작 판정을 내릴 수 없다. |
| 실행기 | 해당 검사·고정 리비전·권한 범위·입출력 계약 | 해당 검사에 한정된 이벤트, 실제 관찰값과 로컬 증거. 제품의 기대 동작과 실행 도구 자체의 오류를 구분한다. |
| 독립 리뷰 | 특정 역할의 자료·평가 기준 목록 | 그 역할의 최초 판정과 원본 증거. 통합자는 봉인된 입력을 모아 의견 충돌을 기록한다. |
| 기록 작성 | 새 회차/시도 식별자, 증거 바이트, 봉인 결과 | 새 저장 경로, 정규 기록, 해시·검증 결과. 관심사가 다른 뷰마다 별도 판정을 저장할 필요가 없다. |
| 표시·인계 | 완결 기록과 읽기 권한이 있는 증거 | 동일 시도의 MD·HTML·인쇄용 HTML/PDF. 누락된 증거의 경로나 상태를 보이게 한다. |
| 선택적 외부 전달 | 봉인 이후의 기록, 전송 승인, 목적지·범위 | 승인된 새 항목의 영수증. 외부 시스템의 수정/장애가 원본에 영향을 주지 않는다. |

**실행기 선택 예시.** 로직 검사는 로컬 인터프리터, 브라우저 키보드 흐름은 해당 엔진, OS 설치/권한은 해당 OS, 카메라 실물 반응은 실기기가 필요하다. 시뮬레이터로 관찰할 수 있는 조건과 실기기가 필요한 조건은 ID를 나눈다. 브라우저 결과를 다른 OS 결과로 채우지 않는다. 실서비스와 비밀값은 이 초안의 실행 범위에서 제외한다.

## 저장과 재실행

기본 저장 위치는 로컬 작업공간이며 명령의 `--store`로 바꿀 수 있다. 예시 계층은 `STORE/round-0001/attempt-0001/record.json`이다. 증거는 이 시도 아래에 저장한다. 이전 기록 참조는 저장소 루트 상대경로, 개별 증거는 attempt 상대경로다. 기록 위치를 이동할 때는 계층과 증거를 함께 이동한다.

| 상황 | 생성할 항목 | 보존할 근거 |
|---|---|---|
| 최초 평가 | 새 회차, 새 attempt | 고정 입력과 최초 증거 |
| 기준 또는 제품 수정 후 회귀 | 새 회차, 새 attempt, `regression` 링크 | 이전 기록 해시와 대상 결함 |
| 같은 회차 재실행 | 같은 회차의 새 attempt, `retry` 링크 | 재실행 사유와 이전 결과 |
| 잘못된 자료·주석의 정정 | 같은 회차의 새 attempt, `correction` 링크 | 어느 원본을 왜 정정했는지, 원본 경로와 SHA-256 |
| 이름 충돌·중도 중단 | 이미 있는 attempt 사용 거부. 다음 번호에 신규 작성 | 성공·실패·미완료 디렉터리와 생성된 모든 증거 |

동시 실행에서 시도 디렉터리를 배타적으로 선점한다. 경로가 이미 존재하면 그 안에 파일을 추가하는 것도 금지한다. 보고서는 원본 시도 밖의 새 출력 폴더에 생성한다. 저장소의 가변 요소를 둔다면 `LATEST` 포인터 또는 별도 색인으로 한정한다. 참조 CLI의 `latest`는 저장 디렉터리에서 경로를 구한다. 원본을 대체할 수 있는 근거는 포인터에 두지 않는다. 이 규약은 ITR 작성자의 동작을 제어한다. 파일 소유자의 수동 수정까지 탐지해야 하는 배포에서는 승인된 외부 앵커에 원본 해시를 보관하거나 읽기 전용 스냅샷을 사용한다.

중단된 attempt에 완결 기록이 없으면 그 단계는 미완료다. 운영자는 남은 로그와 경로를 보존하고 새 attempt에 복구 경위와 그 경로를 남긴다. 완결된 원본은 `previous.record_path`에서 `record.json`을 가리킨다. 미완결 원본은 새 시도에서 `retry` 유형으로만 `reservation.json`과 그 해시를 가리킬 수 있다. `correction`은 완결 기록을 대상으로 한다. 에이전트 교대 시 마지막 기록과 링크 체인, 미해결·차단·미실행 목록을 넘기고 판정이 달라지면 변경 근거를 새 기록에 쓴다.

리플레이 HTML은 완결된 정규 기록 전체를 내장한다. 재생 위치에 따라 상세를 늦게 보여 주는 기능은 기록을 설명하는 화면 동작이다. 원본을 보지 말아야 할 최초 판정자에게는 이 HTML을 제공하지 않는다. 독립성은 입력 배분과 봉인 후 전달에서 확보한다.

## RC에서 실행할 수 있는 어댑터

`tools/project.py`는 [프로젝트 계획](../schemas/project-plan.schema.json)의 파일과 실행 파일 지문을 묶고 승인 후 신뢰된 테스트를 실행한다. 출력/오류는 각각 처음 65,536바이트를 디코딩해 보존한다. 출력 전체를 읽어 지정한 통과 문구가 보존 경계 뒤에서 실제 확인되면 해당 문구와 디코딩 문자 위치를 별도 발췌 필드에 남긴다. 인코딩 기본값은 UTF-8이며 CP949는 계획에 명시한다. 검사별 작업 사본은 파일 상태를 공유하지 않으므로 통합 검사는 필요한 여러 동작을 하나의 승인 명령 안에서 수행한다. 승인 지문에 포함되지 않는 호스트 런타임·OS 라이브러리·도구 체인의 버전은 환경 제약으로 기록한다.

`tools/progress.py --watch`는 가장 최근 회차·시도의 저널을 폴링하고 외부 출력 폴더의 색인만 원자적으로 갱신한다. 진행 중 잠시 보이지 않은 상태는 최종 리플레이에서 확인한다. Windows 공유 잠금 중에도 관찰은 계속되고, 이미 본 봉인·중단 상태의 색인 게시는 잠금 해제 후 재개한다. 미완결·중단·관찰 정지·판정 봉인을 구별한다. 최종 봉인과 이벤트가 맞을 때 그 시도의 고유 결함과 상세 보고서를 연다. 각 명령과 반환 코드의 재현 예시는 [한국어 안내](../README.ko.md)에 있다.

## ANDA 선택적 연동 명세 · 설계만

독립 1차 판정이 모두 봉인되고 사용자가 대상·범위·내용 전송을 승인하면 전달 어댑터를 호출할 수 있다. 제품 인수에 관한 `approval`을 전송 권한으로 재사용하지 않는다. 전송 전 목적지, 수신 범위, 허용 필드·첨부, 회차/시도, 데이터 축소 범위를 확인한다.

- **Notion**은 승인된 부모 아래 새 회차 페이지를 만든다. 정상·실패·차단·미실행 집계와 고유 결함 수, 근거 링크를 담는다. 정정은 원본 페이지를 참조하는 새 페이지다.
- **Discord**는 승인된 채널에 새 메시지 또는 스레드를 만든다. 결함 상세나 로그 원문은 승인 범위에 포함될 때만 옮긴다. 정정은 새 항목에서 원본을 가리킨다.
- 식별 키는 목적지와 `(run_id, round, attempt, record_sha256)`를 함께 사용한다. 부분 성공이나 전송 결과가 불명확할 때는 기존 영수증과 외부 항목을 확인한 뒤 새로 보낼지를 결정한다. 로컬 전송 영수증은 별도 색인에 보관한다. 승인이 없거나 공유 전 봉인이 끝나지 않으면 로컬에서 종료한다.

이 패키지의 합성 실행과 리플레이에는 ANDA, Notion, Discord 계정 연결이나 키가 필요하지 않다.
